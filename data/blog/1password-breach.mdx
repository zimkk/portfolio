# 1Password Breach: What Leaked

On November 25, 2026, 1Password published an incident update that a lot of engineers will read twice. An attacker got into an employee's corporate GitHub account, copied source code from private repositories, reached the CI/CD system, and used that foothold to push malicious code to backend services. That code then pulled administrative account records for a subset of customers.

The part everyone wants to know first: 1Password says vault contents, vault keys, account passwords, secret keys and recovery keys were not accessed. I have no reason to doubt that design claim, and I will explain why it is plausible below. But I do not want the "vaults are safe" headline to hide the more useful lesson, which is about how the attacker got in and what a GitHub account can do inside a modern software company.

A note on sourcing before the analysis. The primary source is 1Password's own post, which I opened directly. Two independent write ups, from The Hacker News and Help Net Security, were both published November 26. When I compared them, they add almost nothing beyond the company statement. They quote it and rephrase it. So treat everything about the attacker's actions as 1Password's account, not as something an outside party verified. I saw other outlets in search results, but I did not open them, so I am not leaning on them.

## What happened, in order

Here is the timeline as the company describes it.

| Date | Event |
|---|---|
| November 19, 2026 | 1Password begins investigating signs that an attacker had access to an employee's corporate GitHub account |
| Between then and disclosure | Attacker reads and copies source code from private repositories, gets into CI/CD, and pushes malicious code to backend services |
| November 25, 2026 | 1Password publishes its incident update |

The company does not say how long the attacker had access, when the account was first compromised, or how the employee's access was obtained. It does not name the attacker, and it does not say how many customers are in the affected subset. Those are the gaps I would watch for in a future update. 1Password says it will keep the post current if anything changes.

The remediation list is what you would hope for: the GitHub account was disabled, the stolen token was revoked, the access the attacker created was removed, and internal credentials that may have been exposed were rotated or revoked. Controls around GitHub, CI/CD and endpoints were tightened, new detections were added, and independent experts were brought in to check the cleanup.

## What data was taken

The attacker downloaded account records for a subset of users. This is the list from the company's post, with my plain reading of each item.

| Field | Why it matters |
|---|---|
| Names and email addresses | The raw material for targeted phishing |
| Account and user identifiers, creation and last sign-in times | Helps an attacker pick active accounts and sound convincing |
| Public keys | Public by design, so low risk on their own |
| SRP protocol parameters | Per 1Password, cannot be used to access an account |
| Tokens in some invitation, provisioning and recovery email links | The one item I would worry about, covered below |
| Internal version and file numeric identifiers | Non-secret metadata |

Names and emails are the boring part and also the part most likely to be used. If you run 1Password at your company, expect fake "your invitation" and "recover your account" emails to start showing up with real names on them. The company itself says to be careful with unexpected emails, texts or calls that mention invitations or account recovery.

## The token detail that deserves attention

Some of the stolen data was tokens that sit inside links in emails 1Password sends for provisioning invites, which are used with the SCIM Bridge or Hosted Provisioning, and for account recovery. The company says a small number of users were in that state during the incident and were specifically notified.

According to 1Password, a token alone cannot get into an account. It has to be combined with either an SSO sign-in or a six-digit code sent to the user's registered email address. And here is the change worth noticing: the company expanded that code from six numeric digits to ten alphanumeric characters.

Let me do the arithmetic, since this is where the decision makes sense. Six numeric digits give one million possible codes. Ten characters drawn from letters and digits give at least 36 to the power of 10, which is roughly 3.7 quadrillion, and far more if upper and lower case both count. The company did not say which alphabet it uses, so I am only giving the lower bound. That is a jump of about nine orders of magnitude, and it turns "an attacker holding a stolen token could try a million guesses" into "not practically guessable".

My read is that the change tells you how the team thinks about the risk. If the stolen tokens were harmless, they would not have touched the code length. They did it because a six digit code is the weak half of a two-part check once one half is public. That is a sensible, quick fix, and it fits with the company's statement that it found no internal evidence of account takeovers using the exposed tokens. Note that wording: no internal evidence is not the same as proof, and nobody outside the company can check it.

## Why the vaults being safe is believable

1Password's design means your vault is encrypted with keys derived from your account password and a secret key that the company says it does not store. In the words of the post, the company cannot access vault secrets, and neither can an attacker who gets into its servers. That is the whole point of the architecture, and it is why a backend compromise like this one can leak names and emails without leaking passwords.

I would add one honest caution. That protection depends on the client code being what it claims to be. The attacker pushed malicious code to backend services, which is bad enough. If someone could push code into the apps or browser extensions that handle your keys, the story would be very different. The company lists apps and browser extensions as not affected, and says it restored clean versions of the affected service. That is the claim I would most like to see independently validated. The company says it brought in outside experts for exactly that, and I hope their findings get published.

## How a GitHub account turns into a backend breach

This is the engineering lesson, and it applies to your company more than the vault question does.

The attacker did not need to break encryption or exploit a database. They needed one employee identity with enough rights in GitHub. From there the path was: read private source, find the CI/CD system, and use what CI/CD can do. Three steps, and every one of them is a normal capability that a developer account has by design.

A few things I think this incident shows, and I am labeling these as my analysis, since the company has not said how the account was taken over:

- **A source code host is a production system.** If a push to a repo can change code that runs in your backend, then access to that repo is access to production, even if nobody calls it that.
- **CI/CD holds the keys.** The company itself says its CI/CD contains infrastructure secrets the product needs to work. That is true almost everywhere. The pipeline is where long lived credentials gather.
- **Token theft beats passwords.** The post says a stolen token was revoked. Tokens, session cookies and personal access tokens can bypass MFA prompts entirely, because they are what you get after the prompt is passed.
- **Review rules matter more than perimeter rules.** The malicious code reached backend services. Branch protection, required reviews by someone other than the author, and signed commits are what stand between one stolen account and deployed code.

I want to be fair here. I do not know if 1Password had those controls turned on, or how the push got through. The post says it tightened GitHub and CI/CD controls afterward, which implies something was loose, but that is an inference, not a finding.

## What I would check this week

If you are a 1Password customer, the company says no action is required on your account. I would still do these things, because they cost nothing.

1. Treat any email about 1Password invitations or account recovery as hostile until you have gone to the app yourself. Type the address or open the app, never click through.
2. If you administer SCIM or hosted provisioning, watch your provisioning and sign-in logs for unexpected invitation or recovery activity around and after November 19.
3. Tell your staff what the phishing is likely to look like. Real names and real work emails make fake messages far more believable.
4. Remember that 1Password will never ask for your account password or Secret Key by email, text or call.

If you run engineering, the more valuable exercise is auditing your own setup as if one developer account were already lost. Here are two quick GitHub checks you can run with the gh command line tool, replacing the placeholders with your own names:

```bash
# members who still have two factor authentication turned off
gh api "orgs/YOUR_ORG/members?filter=2fa_disabled" | jq -r '.[].login'

# deploy keys on a repository, to spot long lived write access
gh api repos/YOUR_ORG/YOUR_REPO/keys | jq -r '.[] | [.title, .read_only] | @tsv'
```

Then work through this gap list:

| Gap | Control I would add |
|---|---|
| One account can push to a deployable branch | Require review from a second person and block self approval |
| Long lived tokens in developer hands | Short lived, scoped tokens, and a regular sweep of personal access tokens |
| CI holds broad secrets | Move to short lived cloud credentials issued per job, scoped to one environment |
| Pipeline can reach everything | Separate build, test and deploy permissions, and gate deploy behind approval |
| Stolen session still works | Shorter session lifetimes for source host and CI, and alerts on new token creation |
| Detection only looks at logins | Alert on unusual clones, bulk repo reads and new CI workflow edits |

If you want a rotation order after an incident like this, mine is: tokens and keys that reach production first, then CI secrets, then anything that can mint other credentials, and last the low value items. Rotation is cheap compared with guessing what the attacker saw.

## My take

I rate 1Password's response well. It disclosed within a week of starting the investigation, wrote a clear list of exactly which fields were taken, said what was not affected, and made a concrete technical change instead of just promising to do better. A lot of breach notices read like they were written to say nothing. This one reads like it was written to be checked.

But two things leave me uneasy. First, the root cause is missing: we do not know how the employee account fell. Until that is public, nobody can tell whether this was phishing, a stolen session, a leaked token or something else, and each of those would call for a different defense. Second, the number of affected customers is missing. A "subset" could be a handful or a very large number, and the company has not said.

The bigger point is that password managers are a high value target by definition, and the attackers know the vault itself is hard. So they go after the people who build the product. That is the same pattern we keep seeing across the industry this autumn: the soft target is the developer identity and the pipeline around it, not the cryptography.

## Key Takeaways

- 1Password says an attacker used an employee's GitHub account to copy private source code, access CI/CD and push malicious code to backend services, starting from an investigation that began November 19, 2026.
- Account records for a subset of users were downloaded, including names, emails, identifiers, public keys, SRP parameters and tokens from some invitation, provisioning and recovery links.
- Per the company, vault contents, vault keys, account passwords, secret keys, recovery keys and the apps and extensions were not affected.
- The recovery and invite code went from six numeric digits to ten alphanumeric characters, which is a very large increase in guessing difficulty.
- Unknown so far: how the employee account was compromised, who the attacker is, how long they had access and how many customers are affected.
- Expect phishing that uses real names and talks about invitations or account recovery. Do not click through, open the app directly.
- For your own team, assume one developer account can be lost: require second person review, shorten token life and keep CI secrets short lived and scoped.
