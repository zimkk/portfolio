# When Workflows Fail at 3 AM: Designing Dead-Letter Queues and Auto-Rollback in n8n

Every engineer who has managed production automations knows the 3 AM dread:
- Step 1 created an invoice in Stripe.
- Step 2 generated a PDF.
- Step 3 attempted to update Salesforce, but Salesforce returned an unexpected HTTP 503.

The workflow crashed midway. 

The customer was charged $500, but Salesforce has no record of the payment, and no email was sent.

If you don't design for **Atomicity, Idempotency, and Dead-Letter Queues (DLQ)**, your automated pipelines will inevitably corrupt your business records.

## The Idempotent Workflow with Global Error Trigger

```
[Workflow Execution Starts]
             │
             ▼
[Generate Idempotency Key: hash(order_id + event_type)]
             │
  ┌──────────┴──────────┐
  ▼ (Step Fails)        ▼ (All Steps Succeed)
[Error Trigger Node]   [Commit State & Clear DLQ]
  │
  ▼
[Dead-Letter Queue (DLQ Table)] ──► [Compensating Rollback: Void Stripe Draft]
```

## Key Rules for Zero-Data-Loss Automations

1. **Pass Idempotency Keys Everywhere**: When calling Stripe, HubSpot, or database endpoints, always pass a deterministic `Idempotency-Key` header. If n8n retries, the upstream API will never create duplicate charges.
2. **Dedicated Error Workflow**: Configure a global **Error Workflow** in n8n settings that captures failed execution payloads, saves them to a PostgreSQL `dead_letter_queue` table, and posts a direct triage link to engineering.
3. **Automate Compensating Transactions**: If step 4 fails, the error handler automatically voids drafts created in step 1.
